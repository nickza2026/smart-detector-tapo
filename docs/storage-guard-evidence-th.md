# หลักฐานตอน storage_path_unsafe

V52 มี diagnostics ของตัวฟังเสียงแล้ว ส่วนการตรวจ metadata ชั่วคราวและ diagnostics ฝั่งตัวส่ง Refueling API ด้านล่างเป็นการแก้ในซอร์สวันที่ 18 พ.ย. 2026 ยังไม่ได้เผยแพร่ ไม่ถือว่าพิสูจน์สาเหตุของ VPS จากภาพ error เพียงอย่างเดียว

เมื่อ guard ปฏิเสธพาธ โปรแกรมเก็บ metadata จากผล `lstat` ที่ใช้ตัดสินใจปฏิเสธ ไม่ตรวจไฟล์ภายหลังเพื่อเขียนทับหลักฐานนั้น ข้อมูลประกอบมี:

- `linked_path`, `non_single_link` หรือ `filesystem_root`
- ส่วนที่ตรวจ เช่น `directory`, `source_root`, `media`, `database`, `journal`, `wal`, `shm`; `path` สำหรับการตรวจพาธอื่น
- `depth=0` คือรายการที่กำลังตรวจโดยตรง, `1` คือโฟลเดอร์แม่, `2` คือแม่ถัดขึ้นไป
- mode, จำนวน hardlink, file attributes และ reparse tag หากมี ค่า `?` หมายถึงไม่มีข้อมูล

รายละเอียดผ่าน final event ของตัวฟังเสียงมายังหน้าจอเดิม บรรทัด “เหตุ guard ล่าสุด” มีเวลาเครื่องที่รับ error และแสดงเวอร์ชัน Python/SQLite ของโปรแกรม รายการล่าสุดยังอยู่ใน RAM แม้กดเริ่มฟังใหม่ แต่ไม่ได้หมายความว่าปัญหานั้นกำลังเกิดอยู่ และหายเมื่อปิดโปรแกรม ไม่เขียนไฟล์เพิ่มในโฟลเดอร์ที่ถูกปฏิเสธ

ไม่ใส่พาธจริง ชื่อบัญชี เนื้อหาฐานข้อมูล exception text หรือ RTSP URL ในข้อมูลประกอบนี้ ช่องที่ไม่อยู่ในรายการที่กำหนด ชนิดข้อมูลผิด หรือเลขเกินขอบเขตถูกปฏิเสธก่อนส่งต่อ/แสดงผล ข้อความแจ้งสุขภาพไปโทรศัพท์ยังใช้ข้อความทั่วไปเดิม

นโยบาย guard ไม่เปลี่ยน: link/reparse point และ regular file ที่จำนวน hardlink ไม่เท่ากับ 1 ยังถูกบล็อก รวมถึงกรณีจำนวนเป็น 0 ไม่แก้ฐานข้อมูล คิว หรือประวัติให้เป็นจบรอบ ส่วน diagnostics ไม่ตัดสินใจเริ่มรับเสียงใหม่ การลองเริ่มใหม่สามครั้งตามคำขอภายหลังเป็นนโยบายแยกใน `rtsp-audio-recovery-th.md`

## Metadata ของไฟล์ SQLite ชั่วคราว

การทดลองสร้าง–ลบไฟล์ธรรมดาใน temp ที่สร้างเองบน Windows ทำให้ guard เดิมเกิด `non_single_link`, `component=journal`, `links=0`, `attrs=32`, `tag=0` ได้จริงโดยไม่มี hardlink ส่วนการทดลอง SQLite DELETE journal เขียนพร้อมกันยังไม่ทำให้เกิดเหตุนี้ จึงพิสูจน์ได้เฉพาะ failure class ของ metadata ระหว่างลบ ไม่ใช่ยืนยันว่า SQLite หรือ VPS เป็นสาเหตุเดียวกัน

เฉพาะ regular file ที่เป็น leaf (`depth=0`) ของ `journal`, `wal`, `shm` และไม่มี reparse indication เมื่อพบ link count 0 จะอ่าน metadata ซ้ำได้หนึ่งครั้ง ไม่มี sleep หรือ loop ไม่จำกัด หากไฟล์หายไปหรือเป็น single-link ที่ปลอดภัยแล้วจึงใช้กติกาเดิมต่อ หากยังเป็น 0 จะปฏิเสธ operation ด้วย `storage_busy` ไม่เปิดให้ค่า 0 ผ่าน การตรวจซ้ำครั้งเดียวไม่รับประกันว่า metadata จะเปลี่ยนทัน จึงไม่เปลี่ยนเป็นยอมรับ 0 เมื่อครบจำนวนครั้ง

Hardlink ตั้งแต่สองชื่อ, symlink/reparse และ database/media/ancestor ที่ไม่ผ่านยังเป็น `storage_path_unsafe` แบบหยุด ไม่มีการตรวจซ้ำเพื่อปลดกรณีเหล่านั้น Subtype สำหรับ metadata busy ที่หลักฐานไม่ตรงเงื่อนไขก็ยังจัดเป็น unsafe

ตัวส่งใช้ busy backoff เดิมจาก 2 ถึงสูงสุด 60 วินาทีโดยรักษา consent และปลายทางเดิม ทุก attempt ตรวจ guard ใหม่ทั้งหมด ขณะยังเป็น 0 จะไม่ทำ SQL/HTTP ต่อหลัง guard จุดนั้น หากค่า 0 ค้างถาวรก็ยังพักและไม่ส่งผ่าน ไม่ถือว่าฟื้นแล้ว นโยบายนี้ไม่ใช่สามครั้ง/15 วินาทีซึ่งเป็นของตัวฟังเสียง

## ตัวส่ง Refueling API

ข้อมูลเจ็ดช่องส่งผ่าน queue boundary พร้อมชื่อ operation ที่กำหนดไว้ เช่น `cleanup`, `pending_jobs`, `mark_delivery`; ไม่ส่ง arguments, event ID, SQL หรือข้อความ exception สถานะแสดงข้อมูลได้ทั้ง `queue_open`, `queue_dispatch`, `queue_close` และทั้งการพัก busy กับการหยุด unsafe

`queue_dispatch` อาจเกิดก่อน HTTP หรือระหว่างบันทึกผลหลัง receiver ACK จึงไม่ยืนยันว่าไม่เคยส่งถึง API และไม่แสดงว่าส่งสำเร็จหากยังบันทึกผลไม่ได้ การลองใหม่หลัง ACK ที่ยังบันทึกไม่สำเร็จใช้ event ID/payload เดิมตาม outbox เดิม ไม่สร้างงานหรือข้อมูลรับเงินใหม่ การปฏิเสธสิทธิ์/WAF ยังหยุดก่อนนโยบาย storage recovery เช่นเดิม

## เริ่มตัวส่งใหม่ภายใต้การยินยอมเดิม

ตามคำขอวันที่ 18 พ.ย. 2026 หลังผู้ใช้กดเริ่มส่งในรอบเปิดแอปนี้แล้ว หาก worker เกิด exception ที่ไม่ใช่ค่าตั้ง/permission ผิด หรือ guard รายงาน `storage_path_unsafe` จะรอ 15 วินาทีแล้วลองใหม่ได้สูงสุดสามครั้ง ไม่กดปุ่ม UI จำลอง ไม่สร้าง consent ใหม่ ไม่เปลี่ยนปลายทาง และไม่ข้าม guard ทุกครั้งเปิด queue ผ่านการตรวจตามเดิม หากเป็น hardlink/reparse จริงและยังไม่หายจะไม่ทำ SQL/HTTP ต่อจาก guard นั้น และหยุดเมื่อครบสามครั้ง

นับหนึ่งครั้งเมื่อส่งงานเข้า worker สำเร็จแล้วเท่านั้น แต่ไม่ถือว่าสำเร็จจน future ของงานนั้นกลับมาโดยไม่เกิด exception จึงรีเซ็ตงบสามครั้ง การรอคิวว่างที่ตรวจฐานและ guard สำเร็จเป็นหนึ่งรอบงานสำเร็จ ไม่ใช่หลักฐานว่า API ปลายทางตอบรับ งานที่ยังไม่จบต้องถูกเก็บผลก่อนเริ่มอีกงาน จึงไม่มี attempt ซ้อนจากการลองใหม่

กดหยุด ปิดแอป แก้ URL/คีย์ในแบบฟอร์ม เปลี่ยนค่าที่บันทึก หรือปิดสิทธิ์ จะยกเลิกการรอ การเปิดแอป/Windows login ไม่ถือเป็นการกดเริ่มส่ง คีย์ถูกปฏิเสธ/WAF, schema/corrupt/camera mismatch และค่าตั้งที่ไม่ผ่านยังหยุดให้ตรวจเอง กรณี submit งานไม่สำเร็จและไม่ทราบว่ารับงานไปแล้วหรือไม่จะหยุดอย่างปลอดภัย ไม่สร้าง pool ใหม่หรือส่งงานซ้ำโดยเดา

นโยบาย busy/full/permission/io recovery และ HTTP retryAt เดิมไม่เปลี่ยน การเริ่มใหม่นี้ไม่ใช่ watchdog ภายนอก จึงไม่เปิดแอปหรือ VPS ที่ดับขึ้นมาเอง และไม่ยืนยันการรับเงินหรือรับ API สำเร็จจากการสั่ง start

การตรวจพาธบน VPS ภายหลังเหตุที่พบปกติไม่ยืนยัน metadata ตอนล้ม และไม่เชื่อมเหตุ PCM ไม่สดก่อนหน้าเข้ากับ storage โดยอัตโนมัติ
