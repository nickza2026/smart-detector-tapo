# SmartTapo .22 candidate — แสดงเหตุผลWebhookไม่ถูกทับ

## เหตุที่เห็น “หยุดอยู่” ตลอด

รุ่นก่อนมีบั๊ก:ข้อความจากการบันทึกหรือเริ่มไม่ผ่านเขียนลงlabelเท่านั้น แต่pollที่ทำงานซ้ำเขียนsender.statusกลับทับทันที จึงซ่อนเหตุผลและทำให้ผู้ใช้กดเดา ไม่ใช่หลักฐานว่าไม่มีคิวหรือปุ่มกดเสีย

.22เก็บข้อความไว้ในสถานะเดียวกัน แยกกรณียังไม่บันทึกสิทธิ์/แก้URLหรือkeyแล้วยังไม่บันทึก/ยังไม่ยืนยันคิว/อ่านคีย์ที่ผูกURL+กล้องไม่ได้ ข้อความยังอยู่หลังpoll แต่เมื่อมีความคืบหน้าส่งจริงหรือreceiverปฏิเสธสิทธิ์ จะเปลี่ยนตามผลจริง กดเริ่มซ้ำขณะเปิดอยู่ไม่บอกว่ายังไม่เริ่มทั้งที่ตัวส่งเดิมยังทำงาน

**ไม่ต้องกดส่งทีละเหตุการณ์:** บันทึกURL/key/สิทธิ์→ยืนยันผูกคิว→เริ่มส่งหนึ่งครั้งต่อsession แล้วส่งคิวใหม่เอง ถ้าไม่มีคิวตัวส่งที่เปิดแล้วต้องรอคิว ไม่ได้หยุดเพราะคิวว่าง ไม่มีการเปิดส่งจากการอัปเดตหรือเปิดแอปเอง และไม่ย้ายคิวที่ผูกปลายทางแล้วโดยเงียบ

หากข้อความระบุคีย์ไม่ตรงURL/กล้องหรืออ่านไม่ได้ ให้กรอกkeyในแอปและบันทึกใหม่ ไม่ส่งในแชต ไม่เดาว่าไฟล์keyมีอยู่แปลว่าใช้ได้ ไม่ข้ามDPAPI bindingหรือทดสอบยิงจริงโดยไม่อนุญาต BaseURLตามสัญญาปัจจุบันเช่น`https://dashboard.example/api` ไม่ใส่endpointเต็ม ส่วนเส้นทางproductionจริงต้องตรวจdeploymentแยก ไม่ได้เรียกเครือข่ายจากงานแก้นี้

## ขอบเขตที่ไม่ได้เพิ่ม

คิวWebhookปัจจุบันยังเป็นรอบเติมจากเสียงและรูปที่เชื่อมกับรอบนั้น ยังไม่ได้ต่อเหตุวัตถุผ่าน/ค้างจากภาพเดี่ยวเข้าAPIโดยตรง ไม่มีการแต่งรอบเติมหรือเวลาเริ่ม/เงินสำเร็จจากความเคลื่อนไหว และยังไม่ได้รับคำยืนยันขยายสัญญาเหตุภาพ/เปลี่ยนเป็นauto-armข้ามsession งานUIประวัติเสียงที่ยังไม่ผูกเป็นรอบยังพักไว้

คงโหมดภาพ.5/ตรวจclock2และกู้known5minContinueจาก.21 กดpresetแล้วSaveหากยังไม่เปิดmode ดู`refueling-v21-th.md` ใหม่เปลี่ยนคำlogเป็น“ผ่านเกณฑ์ความสด”แทน“clockเปลี่ยน”เพราะwindowยืนยันสุขภาพทั้งช่วง ไม่ใช่clockเปลี่ยนทุกภาพ และข้อความรับ/ยืนยันภาพไม่ผ่านไม่ฟันธงว่าADBเสีย จะลองใหม่ตามเดิม ไม่ได้อ้างว่าแก้สาเหตุtransportทุกแบบแล้ว
