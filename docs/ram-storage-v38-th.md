# .38 — แก้เสียง RTSP รีเซ็ตจาก micro-PTS jitter และแยกสถานะให้ตรงจริง

ต้นเหตุที่ทำซ้ำได้: RTSP A-law 8 kHz ส่ง PCM ชุดละประมาณ 100 ms แต่ timestamp มีขั้นเพิ่ม 1 ms ตัวเดิมยอมเพียง 2 ตัวอย่างที่ 16 kHz (0.125 ms) จึงทิ้ง epoch/เริ่มใหม่ถี่ แม้ได้รับ PCM จริง ไม่ใช่เสียงเงียบ

รุ่นนี้ใช้เวลาวิเคราะห์/lease ตามจำนวนตัวอย่างที่ถอดได้จริง ไม่เพิ่มเสียงเงียบ ไม่ทิ้ง/ซ้ำ PCM ไม่สร้าง PTS ที่หาย อนุญาต jitter สูงสุด 1% ของ chunk ก่อนหน้า ไม่เกิน 1 ms และรักษาขอบเดิม 2 samples สำหรับ tiny chunks ตรวจทั้ง source PTS, sample clock และ receive clock พร้อมกัน; คลาด/ค้างสะสมเกิน 2 วินาทียังตัดรอบ

ผล source-native ตัวฟังจริงในข้อมูลทดสอบแยก 120 วินาที ก่อนแก้รีเซ็ต 33 ครั้ง ต่อเนื่องสูงสุด 3.798 วินาที หลังแก้เหลือ 2 ครั้ง ต่อเนื่องสูงสุด 73.798 วินาที รับ PCM 117.294 วินาที สองครั้งที่เหลือเป็น source timestamp เหลื่อม 19/20 ms จึงยังหยุดยืนยัน/เริ่มใหม่ ไม่อ้างว่าระบบต้นทางไม่มีช่องว่างทุกแบบหรือเสียงพร้อมตลอด

UI แยกเวลาเสียงขาด/ซ้อน, ข้อมูลเวลาไม่ถูกต้อง และเสียงล่าช้า/clock คลาดออกจากกัน เมื่อรับ PCM กลับมาแล้วแต่ประวัติยังรอ end หลัง gap จะบอกว่ากำลังรับข้อมูลและรอประกาศสิ้นสุด ไม่กล่าวว่าเสียงกำลังขาด ไม่ปลอม end ไม่ผูกลูกค้าข้ามช่วงที่หาย

ทดสอบ native ไม่เล่นลำโพง/อุปกรณ์เสียง Windows ไม่บันทึก PCM/WAV ไม่ถอดคำพูด ไม่ส่งจริง ไม่เปลี่ยน config หรือประวัติจริง ใช้สำเนาโปรไฟล์เดิมในข้อมูลทดสอบแยก ไม่ได้ยืนยันการรู้จำประกาศจริงทุกสภาพหรือการชำระเงิน ไม่ต้องตั้งค่า/เลือก ROI/โฟลเดอร์ใหม่เพียงเพราะอัปเดตรุ่น; หลังเปิดให้ยินยอมและเริ่มฟังตามเดิม

EXE ต้องผ่าน cold gates เพิ่ม 2 ข้อเป็น 62: clock จิตเตอร์ยังเดินตามตัวอย่าง และ gap/overlap ใหญ่ยังถูกปฏิเสธ รวมการทดสอบ A/V/NCC/ประวัติจำลองและ Save→ปิด→เปิดใหม่ ดู verification.json ของรุ่นนี้ ไม่ใช่ผล native EXE กับ RTSP ส่วนตัว

## ฟังก์ชันภาพ/RAM/ที่เก็บข้อมูลที่สืบทอดจาก .37

# .37 — จัดสรรจุดอ้างอิงให้บริเวณช่องรับ ไม่ให้รายละเอียดไกลแย่งงบ feature

แก้สาเหตุที่ทำให้จัดแนวสลับผ่าน/ไม่ผ่าน: เดิมเลือก ORB 3,000 จุดทั่วภาพก่อน แล้วค่อยตัดเหลือย่าน ROI ทำให้ Full HD เหลือจุดใช้จริงเพียง 20–29 จุด รุ่นนี้เลือก reference feature เฉพาะย่านที่มีสิทธิ์ใช้ตั้งแต่ต้น และเผื่อการค้นหาในภาพปัจจุบันตามระยะกล้องขยับที่ตั้งไว้

ไม่ลดขั้นต่ำ inlier/consensus/การล้อมรอบช่อง/ข้อจำกัดการขยับ/photometric background ไม่เปลี่ยน ROI, reference หรือ configuration ที่ผู้ใช้บันทึก ไม่เรียนรู้วัตถุค้างเป็นพื้นหลัง ไม่เปลี่ยน 10 ภาพและระยะเวลาค้าง และภาพที่จัดแนวไม่ได้ยังเป็น UNKNOWN

หลักฐานก่อนแก้: ผู้ใช้อนุญาตอ่าน RTSP 60 วินาที พบ alignment ไม่ผ่าน 33 จาก 177 เฟรมที่ผ่านเวลา (31 anchors_do_not_surround_slot) Decoder ไม่มี error หลังแก้ source Capture→RAM→Worker ทั้งสายแบบ shadow แยก 60 วินาที วิเคราะห์ 84 เฟรม EMPTY ทั้งหมด ไม่มี alignment UNKNOWN ในรอบนั้น และไม่มี raw frame PNG/SQLite rows ไม่ส่งจริง/ไม่เปิดเสียง ไม่แตะประวัติจริง config/reference hashes ไม่เปลี่ยน

เป็นการทดสอบ native source ในช่วงสั้น ไม่ใช่การรับรอง EXE กับกล้องจริงทุกสภาพ/การหยอดเงินจริง/การแจ้งเตือนถึงโทรศัพท์ ภาพค้างและวัตถุมีการทดสอบจำลองบนภาพตัวอย่างที่เก็บเฉพาะ local; ภาพและ RTSP ส่วนตัวไม่อยู่ใน ZIP หลักฐาน EXE/loopback/full/clean ดู verification.json ของรุ่นนี้

ค่าที่บันทึกเดิมใช้ต่อได้ ไม่ต้องตั้งใหม่หรือเลือกโฟลเดอร์ใหม่เพราะอัปเดตรุ่น รวมแก้ Save/ปิดโปรแกรมจาก .36 แล้ว

## วิธีใช้และข้อจำกัดที่สืบทอดจาก .36

# .36 — แก้ Save โฟลเดอร์แล้วปิดด้วย error

รุ่นนี้แก้ cleanup เสียงที่เรียกปุ่ม Tk หลังหน้าต่างถูกทำลาย ค่าโฟลเดอร์ที่บันทึกสำเร็จไม่จำเป็นต้องตั้งใหม่ การเปลี่ยนโฟลเดอร์ยังปิดโปรแกรมอย่างตั้งใจเพื่อให้เปิดใหม่ใช้ข้อมูลชุดใหม่ แต่ต้องไม่ขึ้นกล่อง Unhandled exception

ตรวจเพิ่มเส้นทาง main จริง: Save → ปิด → finally cleanup → เปิดจาก config เดิมอีกครั้ง และรักษาข้อมูลเก่า/ไม่เปิดสตรีมเอง ไม่ได้แก้ด้วยการกลืน exception ทั้งโปรแกรมหรือข้ามการหยุด runtime

# .36 — RTSP ตรวจใน RAM และเลือกโฟลเดอร์เก็บข้อมูล

ไฟล์ส่งมอบและผลตรวจยืนยันดู `verification.json` ข้างEXE คู่มือนี้อธิบายโหมดGUIใหม่ ไม่ใช่หลักฐานว่าได้ทดสอบกล้อง/เสียง/มือถือจริงแล้ว

## ภาพไปที่ไหน

โหมดหลักของGUIคือ **RTSP → ถอด/ตรวจเฟรมในRAMที่มีขอบเขต → บันทึกเฉพาะเหตุการณ์และหลักฐาน** ไม่เซฟPNG/ready-markerหรือSQLiteแถวเฟรมทุกภาพเหมือนโหมดspoolเดิม และไม่ได้ย้ายปัญหาไปเก็บภาพครบ5นาทีในRAM

ความถี่0.2วินาทีคือขอตรวจ5ครั้งต่อวินาที ไม่รับประกันFPSจริง ถ้าแหล่งภาพ/Workerช้าหรือมีเฟรมขาด ระบบต้องแสดง/ตัดหลักฐานตามจริง ไม่เติมเฟรม ไม่ต่อหลักฐานข้ามช่วงที่ไม่ทราบ และไม่ใช้เวลาเริ่มประมวลผลแทนเวลาถ่ายภาพ

คงเกณฑ์จำนวนภาพและระยะเวลาค้าง เช่น10ภาพพร้อมอย่างน้อย9วินาที ไม่เปลี่ยนกรอบ/thresholdหรืออนุมานจากภาพเก่าหลังStop/restart การรับภาพ เสียง และWorkerยังแยกงานกัน ไม่เริ่มฟังหรือเปิดสตรีมจนผู้ใช้กด/ยืนยันstartupที่ผูกไว้ตามปกติ

## สิ่งที่ยังบันทึกลงดิสก์

- ข้อมูลเหตุการณ์วัตถุปรากฏ/ผ่าน/ค้างและเวลาที่เกี่ยวข้อง
- ภาพอ้างอิงหลักฐานตามจังหวะเหตุการณ์เดิม: ภาพแรกเต็มภาพ/กรอบ,ตอนครบเกณฑ์,ตอนยืนยันเคลียร์
- ประวัติ/หลักฐานเสียงและคิวส่งAPIตามกติกาเดิม ไม่เปลี่ยนจากการย้ายภาพไปRAM

ภาพวัตถุผ่านช่องหรือหายจากกรอบ **ไม่ใช่การยืนยันว่าเครื่องรับเงินสำเร็จ** ไม่ใช้ภาพนับยอดเงินจริง ไม่มีOCR/โมเดลธนบัตรใหม่เพิ่มในงานนี้

ค่าเก็บภาพดิบ5นาทีและสูตรพื้นที่FPS×5นาทีเป็นของโหมดspoolเดิม ไม่ใช่ข้อกำหนดเก็บRAMหรือพื้นที่หลักฐานในโหมดใหม่นี้ หลักฐานเหตุวัตถุค้าง/เหตุผ่านปกติยังใช้retentionเดิม และหลักฐานที่ผูกแจ้งเตือนpending/failed/ambiguousยังไม่ถูกลบทิ้งเพื่อบีบquota

## เลือกไดรฟ์/โฟลเดอร์

หยุดCapture/Worker/เสียงและรอรายการเบื้องหลังให้จบก่อนเลือกโฟลเดอร์ข้อมูลใหม่ ใช้โฟลเดอร์เฉพาะที่ว่างหรือยังไม่มี เช่น `E:\SmartTapo-data` ไม่ใช้รากไดรฟ์หรือโฟลเดอร์ของโปรแกรมอื่น ไม่ตามsymlink/junctionเพื่อเขียนออกนอกปลายทางที่เลือก

เมื่อบันทึกเปลี่ยนปลายทาง ต้องปิดและเปิดโปรแกรมใหม่อย่างเป็นระเบียบ ไม่สลับฐานข้อมูล/หน้าต่างประวัติ/เว็บที่กำลังใช้งานกลางรอบ ข้อมูลใหม่จะเริ่มเก็บในโฟลเดอร์ที่เลือก **ของเก่ายังอยู่ที่เดิม ไม่คัดลอก ย้าย หรือลบอัตโนมัติ** ประวัติของปลายทางใหม่จึงแยกจากชุดเก่า และการเปลี่ยนนี้ไม่ได้คืนพื้นที่ของเก่าให้ไดรฟ์เดิมทันที

config/คีย์เข้ารหัสและภาพอ้างอิงขนาดเล็กยังอยู่ที่รากตั้งค่าเดิม ไม่มีการย้ายบัญชี/คีย์ การเปลี่ยนที่เก็บอย่างเดียวไม่จำเป็นต้องตั้งROIหรือยืนยันภาพช่องว่างใหม่เมื่อแหล่งภาพ/กรอบ/ภาพอ้างอิงเดิมยังตรง แต่ต้องยืนยันสิทธิ์Windows-login startupใหม่ให้ผูกกับที่เก็บใหม่ก่อนใช้automation

## พื้นที่และข้อจำกัด

quotaภาพยังเป็นเพดานหลักฐานที่จัดเก็บ ไม่ใช่การจองพื้นที่ทันที ไม่เพิ่มเพดานจากFPSโดยอัตโนมัติในโหมดRAM และไม่ขยายจนเต็มไดรฟ์ ต้องตรวจพื้นที่ว่างบนไดรฟ์ปลายทางพร้อมheadroomสำหรับการเขียนแบบatomic

พื้นที่เต็ม/เขียนหลักฐานไม่ได้ต้องแสดงข้อผิดพลาดจริง ไม่ใส่DBว่าเก็บภาพสำเร็จทั้งที่ไม่มีไฟล์ และไม่ลบหลักฐานค้างส่งเพื่อแก้พื้นที่ การไม่มีเฟรมใหม่/ไม่มีลูกค้าในช่วงทดสอบไม่ใช่การยืนยันความพร้อมตลอดเวลา

การทดสอบใช้สตรีมภาพ/เสียงจำลองบนloopback,tempDBและoffscreenGUIที่แยกไว้ ไม่ได้อนุญาตเชื่อมกล้อง/ฐานข้อมูล/ผู้ให้บริการจริงเพิ่ม ไม่เปลี่ยนrouting/เสียงWindows/บัญชีหรือทำcommit/push/deploy

## เมื่อ Capture หรือคิวมีปัญหา

`overflow` หมายถึงคิวRAMเต็ม/Workerตามไม่ทัน ต้องเริ่มสะสมหลักฐานใหม่ ไม่ต่อเลขเฟรมให้ดูเหมือนต่อเนื่อง และไม่สลับไปเขียนภาพดิบลงดิสก์ ข้อความเดิมถูกจำกัดความถี่ ไม่สลับhealthy/overflowทุกเฟรมจนlogโต

ข้อผิดพลาดdecoder-IPCที่รู้จักจะเก็บตัวถอดภาพเดิมให้จบก่อนเว้นช่วงและเชื่อมใหม่ ไม่เปิดตัวใหม่ซ้อนตัวที่ยังเก็บไม่จบ ภาพก่อนขาดช่วง/ก่อนเริ่มงานจะไม่ถูกนำมาต่อหลักฐานรอบใหม่ ส่วนดิสก์เต็ม/ไม่มีสิทธิ์/ข้อผิดพลาดอื่นไม่ถูกกลืนแล้ววนretryอย่างไร้ขอบเขต

รหัส `runtime_failure` แสดงขั้นตอนและชนิดที่อนุญาตเท่านั้น เช่น `decoder_ipc`, `frame_publish`, `disk_full`, `permission`, `process_lock`, `unknown` ไม่พิมพ์exceptionดิบ URL คีย์หรือtraceback คำว่าunknownยังหมายถึงไม่ทราบ ไม่ใช่ยืนยันว่าเป็นRTSPหรือพื้นที่

เหตุCapture .33หยุด11:46:38ที่ผู้ใช้ส่งมายังไม่มีexceptionย้อนหลังจึง **ยังไม่ทราบต้นเหตุจริง** การจำลองIPCเสียและแก้reconnectใน.36ไม่ใช่หลักฐานว่าแก้เหตุการณ์นั้นแล้ว หากCapturefailedอย่าถือว่าWorkerยังได้รับภาพใหม่แม้หน้าต่างโปรแกรมยังเปิดอยู่

หากใช้Windows-login startup ให้บันทึก/ยืนยันจากEXEรุ่นใหม่ในตำแหน่งถาวร อย่าอนุมานว่าentryที่ยังชี้EXEเก่าจะเปลี่ยนมาใช้RAMเอง การทดสอบจำลองไม่ได้ยืนยันการล็อกอินWindowsจริง
