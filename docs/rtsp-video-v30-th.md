# SmartTapo .30 — ภาพ RTSP / เสียง Windows แยกการทำงาน

## เปลี่ยนอะไร

ฝั่งภาพรับจาก RTSP โดยตรง ไม่ใช้การจับหน้าจอ MEmu/ADB, UI dump, หน้า Live/Playback ของแอป หรือกรอบนาฬิกา MEmu อีกต่อไป หน้า Capture เดิมและปุ่มตรวจ/เก็บหน้าจอถูกนำออกจากหน้าภาพ กรอกURLได้ในแท็บ **1. ตั้งค่า** ค่าเริ่มต้นคือ`rtsp://127.0.0.1:8554/tapo_c500`

`127.0.0.1`หมายถึงเครื่องที่รันSmartTapo ต้องมีrelayให้บริการสตรีมบนเครื่องนั้นอยู่แล้ว โปรแกรมไม่ได้ติดตั้ง/เปิดrelay/ตั้งVPN/routerให้ และไม่ได้ลองต่อเมื่อเปิดหน้าต่างเฉยๆ รุ่นแรกนี้รับURLrelayที่ไม่มีusername/password/query/fragmentเท่านั้น ไม่รองรับการเก็บรหัสกล้องในURL ไม่ใส่คีย์หรือtokenลงช่องนี้

## ภาพและเสียงแยกกันตามที่ขอ

- **ตัวรับ/ถอดภาพ RTSP** เป็นprocessของตัวเอง มีsupervisor,คิวภาพล่าสุดเพียงช่องเดียว ไม่กองภาพเก่าไว้ให้Workerไล่ตาม ถอดภาพต่อเนื่องเพื่ออ่านtimestampแต่ไม่บีบอัดPNGทุกเฟรมที่ไม่ได้ใช้
- **Workerตรวจแบงค์/วัตถุค้าง** เป็นอีกprocess ใช้กรอบ/ภาพช่องว่างที่ยืนยันแล้ว เก็บประวัติและรูปหลักฐาน รวมแจ้งเตือนแบงค์ติดตามกติกาเดิม ไม่รอให้เสียงจบรอบ
- **รับ/วิเคราะห์เสียง Windowsต่อเนื่อง** แยกprocessเหมือนเดิม ไม่ดึงเสียงจากRTSP ไม่แทนอุปกรณ์ด้วยไมค์/default ไม่เปลี่ยนprofileหรือโมเดลเสียง การหลุดของRTSPไม่ใช่คำสั่งหยุดเสียงถ้าเสียงยังมีหลักฐานต้นทางของตัวเอง
- **GUI** แสดงผลและสั่งเริ่ม/หยุด ไม่ทำdecodeหนักในUIthread ปุ่มหยุดทั้งหมด/ปิดโปรแกรมยังขอหยุดทุกส่วนตามเจตนา

เป็นการแยกpipeline/process ไม่ใช่บังคับCPUcoreหรือจำเป็นต้องเป็นคนละเครื่อง OSเป็นผู้จัดเวลาCPU ภาพตัวอย่างแนะนำ200msไม่ใช่การยืนยันว่าเครื่องรับประกัน5FPS และรอบนี้ไม่ได้เพิ่มโมเดลแยกชนิดธนบัตร/เสียงมอเตอร์หรือเปลี่ยนกติกานับเงิน

## เริ่มใช้กับข้อมูลเดิม

1. หยุดงานและปิดตัวเก่าก่อน เปิด`.tools/diagnostic-v30/SmartTapo.exe` ไม่ต้องลบconfig/data/profile/คีย์เดิม
2. ใน**1. ตั้งค่า**ตรวจRTSP URLแล้วบันทึก ส่วนPushoverและระยะเก็บประวัติยังอยู่เหมือนเดิม การบันทึกไม่ได้ส่งแจ้งเตือน
3. ไป**2. ภาพช่องว่าง** ให้ช่องรับไม่มีแบงค์ค้าง กด**ถ่ายภาพจาก RTSP** ขั้นนี้เริ่มอ่านสตรีมตามคำสั่งผู้ใช้และหยุดตัวอ่านเมื่อได้ภาพ/หมดเวลา ไม่เริ่มWorker/รับเสียง/ส่งแจ้งเตือน
4. โปรแกรมใช้ขนาดภาพจริงและแสดงเต็มเฟรมใหม่ ลากกรอบ/ใช้พิกัดตรงช่องรับ อย่าใช้ตำแหน่งหน้าจอMEmuเดิม ยืนยันว่าช่องว่างและกรอบถูกแล้วกด**ยืนยันและบันทึกภาพช่องว่าง**
5. ไป**3. เริ่ม / หยุด** เริ่มCaptureและWorkerได้แยกกัน แต่ต้องยืนยันแหล่งRTSP/ขนาด/ภาพช่องว่างใหม่ก่อน เปิดเสียงจากแท็บเสียงแยกตามเดิมเมื่อพร้อมและยินยอม

ความละเอียดเปลี่ยน/URLเปลี่ยน/รหัสกล้องเปลี่ยนทำให้ภาพช่องว่างเดิมใช้ยืนยันแหล่งใหม่ไม่ได้ ถ้าเปลี่ยนURLระหว่างกำลังถ่ายภาพ โปรแกรมทิ้งผลเก่า ไม่ผูกภาพจากURLเก่าเข้ากับURLใหม่ ผลที่ยังไม่ยืนยันไม่ใช้เริ่มตรวจแบงค์

การเปิดรุ่นใหม่เพียงอย่างเดียวไม่เขียนทับconfigเดิม เมื่อผู้ใช้บันทึกเปลี่ยนจากADBเป็นRTSPครั้งแรก จะเก็บpublicconfigเดิมไว้ในไฟล์`.pre-rtsp-v30.json`ข้างconfigโดยไม่เขียนทับbackupที่มีอยู่ ใช้ชื่อภาพช่องว่างRTSPใหม่ไม่เขียนทับภาพอ้างอิงMEmuเดิม ประวัติ/รูปหลักฐาน/โปรไฟล์เสียง/คีย์เข้ารหัสไม่ถูกลบหรือเปลี่ยนschema

รูปประวัติเดิมแนวตั้งยังเปิดได้ทั้งGUI/Webเมื่อสตรีมใหม่เป็นแนวนอน ไม่เอาความละเอียดปัจจุบันมาปฏิเสธรูปเก่า แต่ยังจำกัดPNG/ขนาดไฟล์/ด้านภาพ/จำนวนpixelก่อนถอดภาพเพื่อกันไฟล์ผิดรูปหรือใหญ่เกินเพดาน

## เสียงยังใช้แหล่งเดิม

แท็บ **เสียง MEmu / ฟังเติม → แหล่งเสียงเดิม / ADB** เก็บชื่อกล้องในTapo,adb.exe,Serial,MEmu.exeและเวลาตรวจที่จำเป็นสำหรับยืนยันเสียง ย้ายออกจากหน้าภาพ ไม่ได้ใช้ADBจับภาพอีก

ถ้าเดิมฟังTapoผ่านMEmuและWindowsloopback ยังต้องเปิดTapo/ลำโพงและอุปกรณ์เสียงเดิมไว้ เสียงโปรแกรมอื่นในoutputเดียวกันยังปะปนได้ตามข้อจำกัดเดิม RTSPภาพสดไม่ใช่หลักฐานว่าเสียงWindowsมาจากกล้องเดียวกัน ไม่ใช้ภาพRTSPออกLiveLeaseปลอมแทนการยืนยันเสียง

เหตุภาพและเสียงยังเก็บเวลาและเชื่อมตามกติกาเดิม แต่เส้นทางRTSPกับเสียงผ่านแอปอาจมีlatencyต่างกัน ยังไม่ได้วัดphysicalsyncจริง ไม่อ้างว่าเสียง/ภาพตรงกันระดับ200msหรือใช้การตรงเวลาอย่างเดียวรับรองจำนวนเงินจริง

## สถานะและการกู้คืน

- `starting`เริ่มเปิดตัวรับภาพ / `waiting`ยังไม่มีภาพใหม่ ไม่หมายความว่าไม่มีการหยอด
- `timestamp_unconfirmed`กำลังสะสม/ไม่ผ่านหลักฐานเวลา ยังไม่ส่งเป็นภาพสด; timestampหาย/ซ้ำ/ย้อนหลัง/ไล่ภาพเก่ารวดเร็วไม่ถูกยอมรับ
- `healthy`เฟรมผ่านเกณฑ์เวลา/ขนาดของตัวรับ ไม่ใช่ยืนยันเสียง/Worker/providerหรือทั้งระบบปกติ
- `reconnecting`ภาพขาด/เปิดไม่ได้ รอเชื่อมใหม่ เมื่อdecoderตายหรือค้างเกินdeadlineจะเก็บกวาดและเริ่มเฉพาะprocessที่เป็นเจ้าของใหม่ ไม่รีสตาร์ตเสียง/Worker/แอปผู้ใช้
- `stale`ภาพในคิวเกินอายุไม่ใช้ / `geometry_changed`ขนาดไม่ตรงให้ยืนยันภาพช่องว่างใหม่ / `calibration_required`ยังไม่ผูกแหล่งและขนาด / `storage_limit`หยุดเมื่อถึงเพดานภาพ
- สถานะเดิมรายงานไม่ถี่กว่าทุก5วินาที เปลี่ยนสถานะรายงานทันที มีจำนวนถอดภาพ/ข้ามภาพคิวเก่า ไม่ใช่จำนวนแบงค์หรือเหตุการณ์ทางการเงิน

เฟรมมีsource/session/sequenceและหลักฐานของตัวรับ ไม่สามารถเอาmarkerเก่า/รูปแก้ไขมาอ้างเป็นRTSPสดได้ เมื่อหลุด/ย้อนเวลาเริ่มsessionใหม่ ไม่ต่อจำนวนภาพแบงค์ติดข้ามช่วงนั้น ยังคงต้องครบจำนวนภาพ **และ**ระยะเวลายืนยันเดิม ไม่ลดเวลารอแบงค์ติดเพียงเพราะปรับช่วงรับภาพเร็วขึ้น

ลายเซ็นเป็นหลักฐานภายในprocess/บัญชีผู้ใช้ ไม่ใช่การรับรองจากตัวกล้องหรือการป้องกันprocessอื่นในบัญชีเดียวกันที่อ่านข้อมูลลับในโฟลเดอร์ได้

PTSกับเวลารับช่วยยืนยันความต่อเนื่องที่ตัวรับ ไม่ได้ยืนยันเวลาเซนเซอร์กล้องโดยสมบูรณ์ **relayที่เล่นไฟล์ย้อนหลังแบบreal-timeยังอาจผ่านเกณฑ์นี้** ต้องกำหนดURLเป็นแหล่งLiveที่เชื่อถือ ไม่อ้างว่าสามารถแยกLive/recordingได้ทุกกรณี

## Windows startup และขอบเขตการตรวจ

bindingภาพแบบADBเก่าไม่ถูกยอมรับเป็นการยินยอมRTSPโดยอัตโนมัติ หากต้องการstartupให้ยืนยันภาพใหม่และบันทึกยินยอมในรุ่นนี้ ภาพอย่างเดียวไม่ต้องผูกAndroid; ถ้าเปิดเสียงอัตโนมัติยังต้องผูกAndroid/outputGUID/profileเดิมอย่างชัดเจน การพัฒนาไม่ลงทะเบียนหรือแก้รายการstartupจริงให้

ตรวจด้วยข้อมูลสังเคราะห์และRTSP/TCP/RTPบนloopbackportที่testสร้างเอง รวมsource/geometry/PTS/reconnect/คิวล่าสุด/decoderค้าง/หยุด/ประวัติ/แบงค์ติด/shadowแจ้งเตือน/หลายprocess ไม่ถือเป็นผลตรวจC500/H.264/URL8554จริงหรือโทรศัพท์ได้รับแจ้งเตือน ไม่ส่งprovider/ใช้DBจริง/รับเสียงจริง/แตะMEmuระหว่างพัฒนาโดยไม่มีอนุมัติเพิ่ม
