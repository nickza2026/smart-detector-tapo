# SmartTapo .14 — แก้ contention และตรวจกรอบนาฬิกาจาก ADB

รุ่น `2026-10-30.14` เป็นชุดแก้ขั้นที่ 1 ตาม `recommendations-th.md` ไม่ใช่การยืนยันว่าทุกข้อในรายงานผ่านบน VPS แล้ว

## อัปเดตโดยรักษาข้อมูล

ไฟล์อยู่บนเครื่องพัฒนา ไม่ได้ส่งเข้า VPS อัตโนมัติ:

```text
D:\works\smart-detector-tapo\.tools\SmartTapo-v14-capture-fix.zip
```

คัดลอก ZIP ไป VPS → หยุดทั้ง Capture/Worker/เสียง → ปิด EXE เก่า → แทนเฉพาะ `SmartTapo.exe` ในโฟลเดอร์เดิม ไม่ลบ config/data/โปรไฟล์/ภาพอ้างอิง/ประวัติ ใช้บัญชี Windows เดิม รักษา `config.local.json` ข้าง EXE ถ้ามี หรือข้อมูลเดิมใต้ `%LOCALAPPDATA%\SmartTapo` ไม่เปิดสองรุ่นซ้อนกัน

ตรวจข้อความหลังเริ่มงานต้องมี `diagnostics 2026-10-30.14` ชุด prepared-profile ใน ZIP เหมือนรุ่นก่อน ไม่ต้องสร้างโปรไฟล์เสียงใหม่หากใช้ของเดิมได้

## แก้ clock เปลี่ยน=False ทั้งที่เวลาใน Tapo เดิน

1. หยุดทุกงาน เปิด Tapo หน้า Live ของกล้องเดิม ตรวจว่าเลขเวลาใน **วิดีโอ** เดิน
2. ใน SmartTapo กด **ดูภาพอุปกรณ์ ADB (ไม่บันทึก)** ต้องเห็นภาพตรงกับ MEmu ที่กำลังดู ถ้าไม่ตรงให้แก้ Serial ก่อน
3. ดูกรอบ **สีฟ้า** และภาพขยายด้านล่าง นั่นคือบริเวณที่ Capture ใช้เทียบพิกเซลนาฬิกาจริง ไม่ใช่ OCR ถ้าภาพขยายเป็นส่วนหัว Tapo หรือพื้นหลัง กรอบผิดตำแหน่ง
4. ลากครอบ **วัน/เวลาในวิดีโอทั้งหมด** ไม่เลือกพื้นที่เคลื่อนไหว หัวแอป หรือนาฬิกา Android ติ๊กยืนยันแล้วกด **บันทึกเฉพาะกรอบนาฬิกา**
5. ไม่ต้องแก้ JSON กรอบแบงก์และภาพช่องว่างไม่เปลี่ยน หน้าต่างเก่าที่อ้างการตั้งค่าคนละชุดจะไม่ยอมบันทึกทับ หากเปลี่ยนกล้อง/ตั้งค่าแล้วให้ปิดเปิดภาพ ADB ใหม่

เปิดหน้า preview หรือแค่ลากกรอบ **ยังไม่บันทึก** และไม่เริ่มฟังเสียง ภาพอยู่ในหน่วยความจำไม่ถูกเซฟลงดิสก์ การบันทึกกรอบไม่ได้พิสูจน์ว่ากล้อง Live ด้วยตัวเอง และไม่มีพิกัดนาฬิกาใหม่ที่เหมารวมให้ทุก layout

## กรอบตรวจแบงก์จากคลิปเดิม

กรอบ `131×104` เดิมในคลิปที่ส่งทำให้คะแนนเฉลี่ยต่ำกว่าเกณฑ์ ส่วน `100×80` ผ่านในเหตุการณ์นั้น จึงเพิ่มปุ่ม **กรอบจากคลิป 100×80 (ทดลอง)** ที่แท็บภาพช่องว่าง

- ใช้เฉพาะภาพ `720×1280` และพิกัด `249,272,100,80` จากคลิปเดิม ต้องตรวจว่ายังตรงช่องรับจริง
- เลือกแล้วเป็นเพียง preview ยังไม่บันทึก ต้องตรวจว่าภาพอ้างอิงไม่มีแบงก์ ติ๊กยืนยันและบันทึกตามเดิม
- ไม่ลด threshold ไม่เอาภาพที่มีแบงก์เป็นภาพช่องว่าง ผลจากเหตุการณ์เดียวไม่ใช่ความแม่นยำทุกกรณี

## สิ่งที่โค้ดเปลี่ยน

- งานตรวจหน้า Tapo ยังแยกเบื้องหลัง แต่ไม่ใช้ UI-dump lock ขวางการปล่อยภาพ การปล่อยภาพคงตรวจ navigation generation และความสดของหลักฐานก่อน commit
- Worker เจอ decision-lock busy จะเก็บเฟรมเดิมไว้ลองใหม่ตาม poll ไม่เพิ่มจำนวน ไม่ทำเฟรมหลังแซง และตรวจหลักฐานใหม่ทุกครั้ง ความเสียหายของ lock/สถานะไม่ถูกต้องยังไม่ถือว่าปลอดภัย
- ตรวจ Tap to refresh ของกล้องเดิมได้ก่อนบังคับครบปุ่มควบคุมทั้งหมด เพื่อกู้เมื่อ overlay บัง control ได้ ปกติยังยืนยันหน้า Live ตามกติกาเดิม ไม่สุ่ม Back/เปิด Home/login และไม่เพิ่มคำแปลที่ยังไม่มีหลักฐาน
- Log แสดงเหตุผลที่ตรวจ Live ไม่ผ่าน เช่น `[incomplete_live_layout]` แทนข้อความรวมอย่างเดียว

**ยังคงกติกา 10 ภาพสดและ gap เดิม** การยอมเฟรมขาดหนึ่งลำดับ/ไม่เกิน 3 วินาทีเป็นข้อเสนอที่รอยืนยัน ไม่ได้นำไปเปลี่ยนเอง ไม่ขยาย Live TTL หรือเกณฑ์เสียง 2 วินาทีเพื่อซ่อนปัญหา

## ทดสอบจริงรอบถัดไป

เริ่มเฉพาะ Capture/Worker โดยปิดส่งจริงไว้ก่อน ตรวจว่า clock เริ่มเปลี่ยนและกรอบเห็นวัตถุได้ บันทึกช่วงทดสอบพร้อม log ไม่จำเป็นต้องมีลูกค้าจริงหรือเสียเงินจริง ห้ามสรุปว่าโปรแกรมตรวจธนบัตรได้แม่นเพียงเพราะ log หรือการทดสอบจำลองผ่าน

ใช้ VNC/Console session เดียวกับ MEmu ไม่เข้า RDP บัญชีเดียวกันระหว่างเฝ้า ตัวฟังเสียงยังเริ่มเองเมื่อได้รับการเลือกอุปกรณ์/ยินยอมเท่านั้น และหลังปิด VNC Viewer ยังต้องมีหลักฐานความต่อเนื่องจริง

ชุดนี้ไม่ติดตั้ง Task Scheduler/auto-logon, ไม่ต่อ webhook/dashboard ใหม่, ไม่แก้ Driver/registry, ไม่ลบประวัติ และไม่ใช่การทดสอบกล้อง/เสียง/Pushover จริงบน VPS
