# ร่างประวัติการเติมและ webhook — สำหรับทบทวน

**สถานะล่าสุด:** ผู้ใช้อนุญาตออกแบบAPIใหม่รวมรูปและเก็บข้อมูลใหม่ในเครื่อง3วันแล้ว มีSQLite store/checkpoint/outboxและclientส่งรูป→JSONที่ตรวจด้วยHTTPจำลองในloopback ไม่ได้เปลี่ยนDBผู้ใช้/เปิดฟังจริง/ส่งdashboardจริง สัญญาฝั่งรับฉบับปัจจุบันอยู่ [Refueling API v1](refueling-webhook-api-th.md)

Physical diagramปัจจุบันแก้ไขได้: [local storage v1](refueling-local-storage.dbml) ตาราง/JSONร่างเดิมด้านล่างเป็นแนวคิดก่อนพัฒนา ไม่ใช้แทนสัญญาAPIv1หรืออ้างว่าLive provenance fieldsถูกเชื่อมแล้ว

กติกาธุรกิจเรื่องเสียงพร้อมเติมซ้ำ เสียงขอบคุณ และ5นาทีจากประกาศล่าสุดได้รับการยืนยันแล้ว รายละเอียดต้นทางอยู่ [ข้อกำหนด](refueling-history-requirements-th.md) แผนภาพแก้ไขได้ที่ [DBML](refueling-history-draft.dbml) ทั้งหมดเป็นไฟล์ในเครื่อง ไม่ได้ส่งขึ้นเว็บวาด diagram

## ข้อเท็จจริงและขอบเขต

- เสียงพร้อมเติมหมายถึงรับเงินถึงเกณฑ์แล้ว แต่ไม่ทราบยอดจริงและไม่ยืนยันเวลาน้ำมันเริ่มไหล
- เสียงพร้อมเติมครั้งแรกเปิดรอบ ได้ยินซ้ำเป็นรอบเดิมพร้อมปัญหาและจำนวนครั้ง นับจากคนละคำประกาศจริง ไม่ใช่หลายwindowของเสียงครั้งเดียว
- รอเสียงจบเกิน300วินาทีจากพร้อมเติมครั้งล่าสุด: ปัญหา “ไม่พบเสียงจบภายใน 5 นาที” แต่ `ended_at` ยังคงว่าง ไม่มีการยกเลิก/หมดเวลาจากตู้โดยอนุมาน
- เสียงรถ/คุย/กระแทกไม่รีเซ็ตเวลา คำขอบคุณยืนยันจบรอบ แม้มีปัญหาเดิมให้เก็บประวัติปัญหาไว้
- รอบหนึ่งอาจมีหลายปัญหาและหลายภาพ ภาพหยอดแบงค์ก่อนเสียงพร้อมเติมต้องเชื่อมได้ ไม่มีภาพไม่แปลว่าเป็นเหรียญล้วน
- ไม่เปลี่ยนเครดิต/ยอดเงิน ไม่เพิ่มจำนวนลิตรจากเสียง ไม่แปลงประวัติภาพเก่าเป็นเติมสำเร็จย้อนหลัง
- ตัวตรวจออฟไลน์/Replayใช้ทดสอบแม่แบบเท่านั้น ตัวรวมรอบรับเฉพาะข้อสังเกตที่ยืนยันแหล่งLive ความต่อเนื่อง และแยกกรณีcandidateกำกวมแล้ว

## แยกสถานะรอบออกจากปัญหา

| เหตุ | สถานะรอบ | ข้อมูลสำคัญ |
|---|---|---|
| พร้อมเติมครั้งแรก | เปิด/รอเสียงจบ | started_at, last_ready_at, count=1 |
| พร้อมเติมซ้ำ | เปิด/รอเสียงจบ | countเพิ่ม, last_ready_atใหม่, ธงประกาศซ้ำ |
| ไม่มีเสียงจบเกิน5นาที | ยังเปิด ต้องตรวจสอบ | เวลาเกิดปัญหาแยกต่างหาก ended_at=null |
| ขอบคุณ | จบ | ended_atจากเสียง มีปัญหาเดิมก็เก็บไว้ |
| ขอบคุณแต่ไม่มีจุดเริ่ม | ไม่สร้างรอบรับเงินปลอม | เก็บข้อสังเกตให้ตรวจสอบ ยังไม่สมมติ started_at |

แยก state=`open/completed/interrupted` กับ has_issue/รายการปัญหา ไม่ใช้timeoutเป็นเวลาจบ รอบต่อไปเริ่มได้หลังยืนยันขอบเขต ห้ามเอาเวลาพบปัญหาหรือเวลาส่งwebhookมาเป็นเวลาเติม ใน.12ถ้าเสียงขาดขณะรอบเปิดจะคงended_at=nullและปัญหาaudio_source_interrupted แยกรอบเก่าออกจากตัวติดตาม รอactualendก่อนอนุญาตreadyเปิดidใหม่ ไม่ผูกข้ามช่วงไม่ทราบข้อมูลและไม่สร้างmissing-endจากความเงียบที่ไม่ได้รับจริง

## โครงสร้างข้อมูลที่เสนอ

เสนอให้คงSQLiteสำหรับข้อมูลในโปรแกรมเดิมก่อน ไม่ต่อDBของdashboardผ่านInternetโดยตรง ฝั่งdashboardเลือกDBของตนเองและรับผ่านAPI **นี่เป็นข้อเสนอ ยังไม่ได้เปลี่ยนฐานข้อมูลเดิม**

| ตารางร่าง | หน้าที่ |
|---|---|
| refueling_sessions | หนึ่งรอบ/ตัวระบุคงที่/เวลาเริ่ม ล่าสุด จบ/จำนวนประกาศ/รุ่นข้อมูล |
| refueling_announcements | ข้อสังเกตเสียงจริงที่ผ่านการยืนยัน เป็นข้อมูลต้นทางสำหรับจำนวนและเวลา รองรับเสียงจบที่ไม่มีรอบ |
| refueling_issues | ปัญหาแต่ละชนิดและเวลาพบครั้งแรก ไม่ลบเมื่อจบ |
| refueling_evidence | ภาพหลายใบต่อรอบ เป็นหลักฐานที่ยังเปิดได้แม้รูปชั่วคราวเดิมถูกcleanup |
| refueling_webhook_outbox | snapshotที่จะส่ง/รหัสeventคงเดิม/retry status ไม่ใช่ข้อมูลธุรกิจอีกชุด |

- ต่อกล้องมีรอบเปิดได้หนึ่งรอบ ทุกความสัมพันธ์ต้องกล้องเดียวกัน เหตุเสียง/source_keyซ้ำไม่เพิ่มcountหรือrevision
- การเพิ่มเหตุเสียง เปลี่ยนรอบ/ปัญหา และบันทึกoutboxต้องเป็นtransactionเดียว เรียกHTTPหลังcommit ไม่ล็อกDBรอเครือข่าย
- ready_count/last_ready_atเป็นprojectionจากเหตุเสียง ไม่เก็บรายการเวลาซ้ำเป็นarrayในตารางรอบ ปัญหาเป็นหนึ่งแถวต่อรอบต่อชนิด ไม่มีrowใหม่ทุก200msที่poll
- เวลาที่เก็บเป็นinstantUTC; หน้าจอแสดงเวลาไทย ข้อมูลแลกเปลี่ยนใช้RFC3339พร้อมtimezone ตัวอย่างด้านล่างใช้+07:00
- การเปิดรายการเรียงเริ่มใหม่ก่อน ใช้started_at+idเป็นตัวตัดสินเมื่อเวลาเท่ากัน รองรับfilterช่วงเวลา/สถานะ/ปัญหาและsortingแบบallowlist เลือกkeyset paginationไม่บังคับcountทั้งหมด
- ไม่ต้องมีRedisหรือบริการqueueแยกสำหรับขอบเขตdesktopนี้

## รูปและการเชื่อมกับประวัติเดิม

- ไม่ใช้เสียงหัวจ่ายยืนยันจบรอบ และไม่เอาภาพหลังประกาศเพียงอย่างเดียวเป็นช่วงรับชำระ
- ต้องกำหนดlookback/กติกาผูกภาพก่อนประกาศ เพื่อไม่จับรูปของลูกค้าคนก่อนผิดรายการ ส่วนนี้ยังไม่เลือกตัวเลขแทนผู้ใช้
- เก็บsnapshot/pinหลักฐานที่แอปเป็นเจ้าของ แยกอายุจากรูปชั่วคราวเดิม ไม่เปลี่ยนกฎล้างรูปทุกชนิดโดยรวม และไม่ลบต้นฉบับที่ผู้ใช้ส่งมา
- ผู้ใช้ยืนยันประวัติ/ภาพใหม่ในเครื่อง72ชั่วโมงนับจากบันทึกรอบครั้งแรก เพิ่มรูป/ประกาศซ้ำ/retryไม่ต่ออายุ ลบแม้ส่งยังไม่สำเร็จพร้อมสรุป “หมดอายุโดยยังไม่ยืนยันการส่งสำเร็จ” quotaรูปปัจจุบัน512MiBแบบสำรองพื้นที่ก่อนเขียน ถ้าเต็มให้แสดงเหตุผล ไม่เติมภาพนอกช่วงหรือสรุปว่าไม่มีหยอดแบงค์
- dashboardจะกดรูปได้ต้องมีสเปกupload/การอ่านรูปที่ยืนยันสิทธิ์ Windows pathไม่ใช่URL และไม่เปิดpublic image endpoint/ส่งWAVเสียงสนทนาให้อัตโนมัติ

## ข้อมูล webhook — APIใหม่ที่อนุญาตให้ออกแบบแล้ว

ไม่มีAPIเดิมให้ยึด ผู้ใช้ยืนยันให้ส่งรูปด้วย จึงกำหนดPUTภาพทีละไฟล์ก่อนPOSTJSONตาม [สัญญาฉบับเต็ม](refueling-webhook-api-th.md) แทนส่งlocalpathหรือmultipartขนาดใหญ่ ยังไม่ได้deployตัวรับจริง

เสนอส่งsnapshotเมื่อเริ่ม/ประกาศซ้ำ/พบปัญหาไม่มีเสียงจบ/จบ ให้dashboardอัปเดตรอบเดิม ไม่เพิ่มธุรกรรมตามจำนวนประกาศ

| เหตุภายใน | event_typeที่เสนอ |
|---|---|
| เริ่ม | refueling.started |
| ประกาศซ้ำ | refueling.attention_required |
| เกิน5นาที | refueling.attention_required |
| ขอบคุณ | refueling.completed |

ตัวอย่างรอบที่ประกาศ2ครั้งและยังไม่พบเสียงจบ:

```json
{
  "schema_version": 1,
  "event_id": "example-round:3",
  "event_type": "refueling.attention_required",
  "occurred_at": "2026-10-28T22:31:11+07:00",
  "session": {
    "id": "example-round",
    "camera_id": "cabinet-1",
    "revision": 3,
    "state": "open",
    "started_at": "2026-10-28T22:26:00+07:00",
    "last_ready_at": "2026-10-28T22:26:10+07:00",
    "ended_at": null,
    "ready_count": 2,
    "has_issue": true,
    "issues": [
      {"code": "ready_prompt_repeated", "detected_at": "2026-10-28T22:26:10+07:00"},
      {"code": "completion_not_detected", "detected_at": "2026-10-28T22:31:11+07:00"}
    ],
    "amount_baht": null,
    "evidence": []
  }
}
```

- `event_id`คงเดิมเมื่อretry; `session.id`คงเดิมทั้งรอบ; `revision`เพิ่มเมื่อข้อเท็จจริงเปลี่ยน ไม่เพิ่มเพราะretry
- ฝั่งรับdeduplicateด้วยevent_id และไม่ให้revisionเก่าทับใหม่ การส่งat-least-onceไม่ใช่exactly-once ห้ามบวกready_countเป็นจำนวนลูกค้าหรือยอดเงิน
- `has_issue=true`และissuesต้องส่งไปด้วยทั้งตอนพบปัญหาและตอนจบภายหลัง เพื่อไม่ให้ปัญหาหายจากdashboard
- `ended_at=null`แปลว่ายังไม่พบเวลาจบ ไม่ใช่เริ่ม/จบเท่ากัน `amount_baht=null`คือไม่ทราบ ไม่ใช่0หรือ10บาท
- ตัวอย่างevidenceว่างหมายถึงsnapshotนั้นยังไม่มีรูปเชื่อม รูปที่มีจริงต้องPUTสำเร็จพร้อมackid/hashก่อนPOST metadata ไม่แนบlocalpathหรือsecretลงpayload
- ส่งสำเร็จหมายถึงAPIตอบรับตามcontract ไม่ใช่หลักฐานว่าผู้ใช้เปิดดูแล้ว ต้องมีสถานะรอส่ง/ส่งแล้ว/ผิดพลาดและแยกrevisionล่าสุดที่ยังค้าง
- เปลี่ยนURL/credentialไม่ควรส่งqueueเก่าไปปลายทางใหม่โดยเงียบ ต้องกำหนดการย้าย/พักqueueให้ชัด ไม่มีการค้นหาkeyหรือทดสอบserviceจริงในขั้นร่าง

## สิ่งที่ทำแล้วกับสิ่งที่ยังไม่ทำ

- มีoffline matcherและpureตัวรวมรอบ ไม่มีcapture/HTTP/SQLในสองส่วนนี้
- ตัวรวมรอบแยกเสียงซ้ำจากwindowซ้ำ เก็บsnapshotimmutableพร้อมsession revision/event key ไม่ยอมให้เสียงเก่ารีเซ็ตเวลา ไม่สมมติจบและไม่สร้างรอบจากขอบคุณที่ไม่มีเริ่ม
- ต้องป้อนเหตุการณ์ตามsource-timeและเลื่อนtimerเฉพาะtimelineเสียงที่ประมวลผลแล้ว ไม่เอาwall clockวิ่งแซงเสียงที่ยังรอจำแนกจนแจ้ง5นาทีก่อนประโยคที่ค้างอยู่จะถูกตรวจ
- เพิ่มdurable recovery/transactional source dedupe/immutable outbox/ภาพcopyที่เป็นเจ้าของเอง/cleanup72hและclientPUTภาพ→POSTJSONแล้ว พิสูจน์ด้วยฐานทดสอบและHTTPจำลอง ยังไม่มีLive listenerที่สร้างรายการจริงหรือbackend/dashboardที่deployจริง
- มีหน้าประวัติเติมสำหรับอ่านข้อมูลใหม่ แยกของเก่า ไม่สร้างตัวอย่างเป็นรายการจริง เปิดโปรแกรมไม่เริ่มฟัง/ไม่ส่งข้อมูลเอง
- ตัวตรวจLiveเดิมอิงชื่อปุ่มที่อาจยังอยู่ในPlayback จึงยังไม่อนุญาตให้เสียงย้อนหลังสร้างรายการเติม ต้องได้signatureหน้าLive/Playbackจริงมาทดสอบก่อน มีcollectorที่ผู้ใช้กดเอง เก็บเฉพาะresource-id/control markers/activity ไม่เก็บภาพ/rawXML/ข้อความบัญชี และoperator-labelไม่ใช่trusted proof
- SQLiteใหม่อยู่ในnamespace `data_dir/refueling/refueling.sqlite3` ไม่ได้เพิ่มตารางหรือเปลี่ยนcleanupในworker.sqlite3เดิม canonical source spansและปัญหาเก็บแยกจากaggregate checkpoint; session scalar columns/indexใช้สำหรับlist/cleanup ไม่อ่านJSONทุกแถวเพื่อตัดสินอายุ

## จุดตรวจรับก่อนเชื่อมจริง

1. สร้างตัวรับdashboardตามAPIv1และทดสอบbody/auth/idempotency/revision/HTTP errors/รูปตามcontract ไม่ส่งtokenในแชต ไม่อ้างว่าHTTPจำลองคือserviceจริง
2. กติกาผูกภาพก่อนพร้อมเติม/หลังประกาศยังต้องระวังขอบลูกค้าคนก่อน ไม่เลือกภาพนอกช่วงโดยเงียบ ระยะ3วันได้รับการยืนยันแล้ว ไม่ถามซ้ำ
3. ฐานทดสอบแยกตรวจrollback/recovery/duplicate/หลายconnection/cleanupรูปแล้ว ขั้นruntimeยังต้องประกอบsource/provenance/การผูกภาพให้ครบก่อนสร้างรายการจริง
4. ฟังต่อเนื่องต้องexplicit operator enable +trustedLive +health/gap gating ไม่ใช้Playbackสร้างรายการ และทดสอบVPSหลังdisconnectRDPจริง
5. ประเมินประกาศรอบอิสระเพิ่ม เสียงคุย/ท่อดัง และกรณีถูกกลบ ไม่อ้างaccuracyจากไฟล์แม่แบบเองหรือmixturesที่สร้างจากไฟล์เดิม
