# .33 — เฟรมRTSPหลายภาพอยู่ในreceive tickเดียวกัน

ปิด .32 แล้วเปิด `SmartTapo.exe` .33 ใช้config/กรอบ/ภาพอ้างอิงเดิมเมื่อยังถูกต้อง ไม่ต้องทำให้แบงค์ค้างจริงเพื่อเปิดตัวตรวจ ดูกติกาวัตถุค้างและmarkerเก่าใน `docs/worker-roi-v32-th.md` และคู่มือเสียง/startupใน `docs/rtsp-audio-v31-th.md`

## สาเหตุที่พิสูจน์ได้

ผู้ใช้อนุมัติอ่านmetadataRTSP20วินาที ไม่บันทึกภาพ/เสียง ไม่เปลี่ยนconfigหรือส่งprovider URLที่บันทึกไม่ใช่localhostค่าเริ่มต้น การอ่านจากปลายทางที่บันทึกได้349เฟรมในช่วงอ่านประมาณ20วินาที

PTSของภาพเดินต่อไม่มีซ้ำ/ย้อนหลัง แต่หลายเฟรมมีเวลาreceiveเท่ากัน นาฬิกาWindows/Python3.12เครื่องนี้เป็นGetTickCount64ละเอียด15.625ms และการส่ง/ถอดเฟรมเป็นกลุ่มทำให้dt=0ได้ ไม่ใช่หลักฐานว่าภาพต้นทางหยุด

โค้ดเดิมบังคับdt>0ทุกเฟรม จึงรีเซ็ตpriming/sessionผิดกรณีนี้ Replayข้อมูลจริงชุดเดียวกัน: เดิมผ่าน12/349ต่อเนื่องสูงสุด3เฟรม; หลังแก้ผ่าน272/349ต่อเนื่องสูงสุด255เฟรม และ100เฟรมท้ายผ่านครบ ส่วนต้นที่เป็นbuffer/primingยังถูกปฏิเสธตามเดิม เปลี่ยนไปใช้POS_MSECอย่างเดียวไม่ได้แก้อาการ จึงไม่เปลี่ยนวิธีอ่านPTSโดยเดา

## สิ่งที่แก้และสิ่งที่ไม่เปลี่ยน

ยอมรับreceive tickเดียวกันได้เมื่อPTSยังเดินหน้า แต่ยังตรวจPTSซ้ำ/ย้อนหลัง/ไม่มีค่า,receiveเวลาย้อน,ช่องว่างเกินกำหนด,ความต่างmedia/receiveเกิน0.25s และต้องprimeครบ1วินาที การburst/replayเร็วหรือreceive clockหยุดยังผ่านไม่ได้

ไม่ปิดtimestampguard ไม่เพิ่มTTL ไม่ลดจำนวนภาพ/ระยะเวลาค้าง ไม่แก้ROI/thresholdหรือclassifier ไม่เปลี่ยนคีย์/ฐานข้อมูล/ภาพอ้างอิงจริง ไม่เพิ่มMEmu/Windowsloopbackกลับมา
